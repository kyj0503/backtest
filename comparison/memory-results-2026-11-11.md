# Python / Rust 메모리 비교 — 2026-11-11

이 문서는 수정 전 측정을 보존한다. 최신 결과는 [수정 후 메모리 보고서](memory-results-fixed-2026-11-11.md)이며, 최종 이미지의 최대값은 Python 243.00 / Rust 45.85 MiB다.

**동일 입력으로 시험한 API 컨테이너의 전체 최대 메모리는 Python 237.31 MiB, Rust 45.96 MiB였다. 이번 실행에서 Rust가 약 80.6% 적었다.** 기존 성능 시험의 실행 전후 스냅샷에 더해 요청 실행 중 메모리를 별도로 측정했다.

## 조건과 측정 방법

- 2026-11-11 16:59~17:01 KST. 기존 네 서비스는 유지하고 동일 이미지의 임시 API 두 개를 새로 생성했다. 각각 CPU 2개·메모리 2 GiB, 서버 프로세스 1개. 앱 코드는 변경하지 않았다.
- Python 이미지 `sha256:6f622a697e0b65e197cdd7959f7e6f913a80ba25d2c4b7b6d5f622f774837c3c`, Rust 이미지 `sha256:ed5f4d927ba1cd1a0628eeb3c5218291c1c343341cbe2242782e0ea152de3afa`.
- API 프로세스는 새로 시작했지만 각 구현의 기존 MySQL 시세 캐시는 유지했다. 완전한 콜드 시스템 측정이 아니다.
- [기존 보고서](results-2026-11-11.md)의 정상 시나리오 37개를 같은 순서로 각각 **10회** 호출했다. 이어 미국 5종목·8년 입력으로 서로 다른 클라이언트 2·8·16개 동시 요청을 각각 한 번 수행했다. 구현당 **396개 요청**, 전체 **792개가 모두 HTTP 200**이었다.
- 구현별 40개 측정 구간이다. 시나리오마다 재시작하지 않았으므로 앞선 요청의 캐시·스레드·할당기 메모리가 다음 구간에 포함된다. 각 시나리오의 독립 최소 필요 메모리를 뜻하지 않는다.
- 요청 발행과 관측은 대상 API와 **다른 cgroup의 별도 컨테이너**에서 수행했다. 관측기의 Python 인터프리터·HTTP 버퍼는 API 메모리에 포함되지 않는다. 대상 cgroup과 PID 정보는 읽기만 했다.
- Python 시험 완료 후 Rust를 측정했다. 단일 실행이며 장기 메모리 누수 검증이나 통계적 반복 실험은 아니다.

단위는 **MiB = 1,048,576 bytes**다.

| 항목 | 수집원 | 의미 |
| --- | --- | --- |
| 컨테이너 현재 메모리 | cgroup v2 `memory.current` | 대상 cgroup에 청구된 익명 메모리·파일 캐시·커널 메모리 등을 포함 |
| 전체 시험 최대 | `memory.peak` | 새 컨테이너 생성 이후 커널이 기록한 최대값. 시작 과정·healthcheck도 포함 |
| 구간 관측 최대 | `memory.current` 샘플의 최댓값 | 실제 순간 피크의 하한. 짧은 증가를 놓칠 수 있음 |
| 프로세스 RSS | PID 1의 `/proc/1/status` `VmRSS` | 별도의 프로세스 상주 메모리 관측값. 공유 페이지도 포함되므로 cgroup 값과 같지 않음 |
| Docker CLI 방식의 근사 작업 집합 | `memory.current - inactive_file` | 원본 JSON에 함께 저장. 아래 표는 이 값 대신 `memory.current` 사용 |

1ms 간격을 요청했다. 실제 구간별 중앙 간격은 Python **1.30~1.35ms**, Rust **1.30~1.56ms**, 가장 큰 관측 공백은 **9.42ms / 9.99ms**였다. 특히 짧은 Rust 요청에서는 구간 피크를 놓칠 수 있어 전체 최대는 샘플링에 의존하지 않는 `memory.peak`로 확인했다. 앞선 시간 성능 표는 관측기를 실행하지 않고 측정한 값으로 유지한다.

공유 파일 페이지의 cgroup 청구 위치와 캐시 상태가 수치에 영향을 줄 수 있다. 컨테이너 값은 프로세스 RSS와 구분하고 호스트 전체 RAM 절감량으로 그대로 해석하지 않는다. MySQL·프론트엔드·브라우저는 API 측정에 포함하지 않았다.

## 기존 서비스 전체의 스냅샷

사용자가 직접 비교하는 기존 서비스의 `docker stats --no-stream` 관측값이다. 위의 새 API 시험과 별개이며 최대값이 아니다. Docker CLI는 파일 캐시 일부를 제외하므로 `memory.current` 표와 직접 섞지 않는다.

| 구성 요소 | Python 쪽 | Rust 쪽 |
| --- | ---: | ---: |
| 기존 API | 291.3 MiB | 26.31 MiB |
| React/Vite 프론트엔드 | 875.6 MiB | 883.0 MiB |
| MySQL | 461.4 MiB | 444.2 MiB |
| 위 3개 단순 합계 | 1,628.3 MiB | 1,353.51 MiB |

이 스냅샷의 전체 구성 합계 차이는 약 **16.9%**다. 양쪽 모두 React/Vite 개발 서버를 사용하므로 API의 80.6% 감소를 서비스 전체에 적용하면 안 된다. 브라우저와 Docker VM 자체의 메모리는 이 합계에도 포함되지 않는다. 운영용 정적 프론트엔드의 사용량도 별도 확인이 필요하다.

## 원본과 재현

원본 디렉터리: `../.comparison/reports/memory/` (Git 제외).

- `python.json`, `rust.json`: 준비 상태, 40개 구간의 요청 전/관측 최대/완료 후 값, HTTP 상태, 종료 상태.
- `<구현>-<시나리오>-samples.json`: 실제 시각과 바이트 단위 샘플, 누적 피크·RSS·스왑 등.
- `runtime-evidence.json`: 이미지 ID, CPU/메모리 제한, 시작 시각, health·OOM·재시작 상태.
- `original-stack-snapshot.jsonl`: 기존 여섯 컨테이너의 Docker CLI 출력.

백엔드 저장소 PowerShell에서 재실행한다. 기존 비교 스택과 `.comparison/reports/scenarios/normal.json` 및 시나리오 입력이 필요하다.

```powershell
./scripts/benchmark-local-memory.ps1
```

스크립트는 새 시각 이름의 결과 디렉터리를 만들며 기존 디렉터리를 덮어쓰지 않는다. 임시 API만 생성·제거하고 기존 비교 서비스와 DB 볼륨을 유지한다. 이번 시험의 임시 API와 관측 컨테이너는 측정 후 제거했으며 기존 네 앱과 두 DB는 정상 실행 중이다.

기존 보고서의 환율 날짜·API 계약 차이는 여전히 남아 있다. 메모리 결과는 해당 문제를 해결했다는 의미가 아니다.

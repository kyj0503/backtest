## 결과를 바꾸는 차이

### 1. 환율 날짜가 하루 앞당겨지는 문제 — 우선 수정 필요

`backtest_be_rust/src/data.rs`의 `parse_chart`는 Yahoo 메타데이터의 현재 `gmtoffset`을 모든 과거 타임스탬프에 더한다. 과거 날짜별 서머타임을 처리하지 않는다.

실제 Yahoo 응답은 `exchangeTimezoneName=Europe/London`, 현재 `gmtoffset=0`이었다. `2023-04-13T23:00:00Z`의 환율은 런던 현지 날짜 **4월 14일**에 속한다. Rust는 **4월 13일**로 저장했다. 양쪽 DB와 원본 응답으로 확인했다.

| KRW=X 저장 날짜 | Python 종가 | Rust 종가 |
| --- | ---: | ---: |
| 2023-04-12 | 1322.0900 | 1322.8300 |
| 2023-04-13 | 1322.8300 | 1301.4301 |
| 2023-04-14 | 1301.4301 | 해당 날짜 관측값 없음 |

KRW 환율 참고 조회에서 156개 날짜가 달랐다. JPY·EUR 환율에서도 같은 이동을 확인했다. 다음 날짜의 환율을 이전 날짜 평가에 사용하므로 과거 시점 계산에 미래 데이터가 섞이는 문제가 된다.

### 2. 요청 기간 밖 주가와 응답 필드 차이

- `/prices`에 삼성전자 `2023-01-03~2023-10-31`을 요청했을 때 Python은 203개, Rust는 204개 가격을 반환했다. Rust의 마지막 가격은 **2023-11-01**이다. Yahoo 요청 경계와 거래소 현지 날짜 변환 후 범위 필터를 확인해야 한다. 이 시험의 핵심 계산 곡선 날짜 수는 양쪽이 같았으나 참고 데이터 API 응답은 달랐다.
- Rust의 `ticker_info`에는 Python에 있는 `first_trade_date`가 없었다. 참고 조회를 생략한 POST에서도 Python은 최소 티커 정보를 반환하지만 Rust는 빈 객체를 반환한다.
- 기술 전략의 거래 보유기간 형식: Python `P160DT0H0M0S`, Rust `160 days 00:00:00`. 문자열 형식에 의존하는 API 사용자는 영향을 받는다.
- Python의 전략별 `Entry_*`/`Exit_*` 지표 진단 컬럼은 Rust에서 생략된다. 기존 마이그레이션 문서에 기재된 차이다.
- 빈 포트폴리오 등에서 상태 코드는 양쪽 모두 422지만 Python은 `detail` 배열, Rust는 `detail` 문자열을 반환한다.

### 3. 동일 시세로 분리 확인한 계산 결과

두 DB를 읽기 전용으로 스냅샷하고, **Python DB의 동일 OHLC·환율 관측값**을 양쪽 엔진에 주입했다. 외부 조회·DB 접근·상장일 검증·참고 데이터 수집은 이 재실행의 대상이 아니다. 실제 HTTP 시험과 구분해야 한다.

- 계산 32개에서 최대 평가금액 차이는 **$8.74×10⁻¹⁰ 미만**이었다.
- 삼성전자 SMA 최종금액도 $9,792.846910446013 / $9,792.846910446004로 일치했다. 미국 5개 기술 전략의 기본·변경 파라미터, 적립, 리밸런싱, 여러 통화도 포함했다.
- 성과 지표는 29개 사례에서 `max(1e-6, abs(expected)×1e-6)` 허용 오차 이내였다. 나머지 3개는 DCA 일별 상승·하락 횟수 차이였다.
- 6개월 DCA 사례의 상승일: Python 672 / Rust 670, 일별 승률 53.4181% / 53.2591%. Python의 약 `1.4e-14%`, `1.7e-14%` 수익률을 Rust가 0으로 계산하는 날짜가 원인이다. 최종금액은 같아도 일별 집계가 달라진다. 3개월·12개월 DCA에서도 하락일이 1일씩 달랐다.

즉 이번에 발견한 큰 금액 차이는 데이터 수집/정규화 경로에서 발생했다. 모든 가능한 계산 입력의 동등성이 증명된 것은 아니며, 미세한 0 판정과 응답 형식은 별도 정합성 문제가 남는다. 실제 미국 기술 전략 사례의 작은 금액 차이도 같은 시세를 사용하면 사라졌다.

근거: `replay-both.json`, `replay-summary.json`; 재실행 도구: `snapshot-prices.py`, `replay-python.py`, `replay-rust.rs`.

## 입력 검증과 부분 실패

35개 경계 사례 중 **30개는 HTTP 상태가 같고 5개는 달랐다**. 상태가 같아도 오류 메시지·응답 형식까지 같다는 의미는 아니다.

| 입력 | Python | Rust |
| --- | --- | --- |
| `amount: "10000"` | 200, 숫자로 변환 | 422 |
| `amount: true` | 200, 숫자로 변환 | 422 |
| RIVN 상장 전 2020년부터 요청 | 200, 실제 상장일 2021-11-10부터 계산 | 422, 시작일 이후 상장 종목 거부 |
| `rebalance_frequency: null` | 422 | 200 |
| GET에 `start_date` 두 번 전달 | 200 | 422 |

이 중 엄격한 타입 검증·중복 인자 거부는 더 엄격한 정책일 수 있다. 다만 기존 클라이언트와의 호환성 차이이므로 의도한 계약을 정해야 한다. 상장 전 시작일 처리 역시 일괄 마이그레이션 전에 결정해야 한다.

양쪽 모두 거부한 사례: 빈/중복 포트폴리오, 0·음수 금액, 금액/비중 혼용, 금액 누락, 부적절한 심볼·전략·파라미터·수수료, 30일 미만·역순·미래·10년 초과 날짜, 지원하지 않는 DCA, 기술 전략+DCA/리밸런싱, 21개 자산, 잘못된 GET 인자·뉴스 개수·JSON. 잘못된 HTTP 메서드는 모두 405였다.

존재하지 않는 종목 단독은 양쪽 422, AAPL과 함께 넣으면 양쪽 200이었다. 실패한 종목을 경고와 함께 제외하고 해당 투자금을 수익률에서 빼는 처리는 같았다. 경고 문구의 상세 금액 표시는 달랐다. `CASH`를 주식 유형으로 전달하면 양쪽 모두 실제 CASH 티커를 조회했다.

| 8 | 8/8 · 3,714.59 ms | 8/8 · 58.73 ms |
| 16 | 16/16 · 7,792.69 ms | 16/16 · 127.39 ms |

동일 클라이언트의 8개 동시 요청에서는 양쪽 모두 2개 성공·6개 429였다. 16개에서는 Python 2개 성공·14개 429, Rust 4개 성공·12개 429였다. Rust가 빠르게 완료되어 후속 요청이 빈 슬롯에 진입할 수 있으므로 이 수치가 동시 실행 제한 2개를 위반했다는 증거는 아니다. 정확한 서버 도착 순서나 최대 동시 실행 수를 추적한 시험은 아니다.

429 응답의 `Retry-After`는 Python **10초**, Rust **2초**로 달랐다. 배치별 성공 건수/벽시계 시간은 원본에 있지만 지속 가능한 처리량으로 해석하지 않는다.

## 실제 브라우저

Chromium에서 폼을 직접 조작해 AAPL 매수 후 보유, 삼성전자 SMA, 매월 $500 AAPL 적립을 양쪽 모두 실행했다. 각 사례에서 계산 POST + 주가·환율·벤치마크·뉴스 GET이 모두 200이었고, JavaScript 페이지 오류가 없었다. 차트 로딩 종료, CSV 파일의 실제 다운로드까지 확인했다.

첫 브라우저 실행에서 실행 버튼 클릭부터 다섯 API 응답 및 CSV 버튼 표시까지 Python은 약 0.91~1.38초, Rust는 약 0.81~1.01초였다. 반복 브라우저 실행에서는 Python 0.75~1.08초, Rust 0.70~1.14초였다. 각 사례 한 번씩의 관측값이고 개발 모드 렌더링·프록시·브라우저 비용이 섞인다. **API가 수십 배 빨라져도 화면 체감 속도가 같은 비율로 좋아진다고 할 수 없다.**

증거: `ui-first.json`, `ui.json`, `ui/`의 각 구현별 PNG·CSV. 한글 화면 캡처는 검증용 브라우저에 Windows 맑은 고딕을 읽기 전용으로 마운트해 다시 찍었다. 실행 중인 프론트엔드는 변경하지 않았다.

## 판단과 확인 범위

우선순위는 **환율의 과거 시간대 처리 및 오염된 비교 캐시 재수집 → 참고 주가의 날짜 경계 → API 입력/응답 계약 → 부동소수점 0 판정**이다. 수정 후 이 입력과 고정 시세 시험을 다시 수행해야 한다.

이번 비교는 실데이터와 사용자 화면에서 이전보다 강한 근거를 확보했지만, 인증이 켜진 운영 환경·실제 뉴스 데이터·외부 서비스 장애·장시간 부하·ARM64를 검증하지 않았다. 로컬 Turnstile은 꺼져 있고 네이버 인증값이 없어 뉴스는 빈 결과 경로다. CPU의 피크와 p95/p99도 측정하지 않았다.

앱 네 개와 두 비교 DB는 실행 상태로 유지했다.

- Python 화면: <http://localhost:5173/backtest> / API: <http://localhost:8000>
- Rust 화면: <http://localhost:5174/backtest> / API: <http://localhost:8001>

## 재현과 원본

전체 원본 디렉터리: `../.comparison/reports/scenarios/` (Git 제외). 각 정상·경계 사례 디렉터리에 `input.json`, 구현별 최초/마지막 응답을 보관했다. `normal.json`에는 6회 전체 시간과 구조·값 차이, `boundary.json`에는 경계 결과, `concurrent.json`에는 배치별 요청 상태가 있다. 파일의 첫 응답과 마지막 응답은 수집·DB 반올림·메모리 캐시에 따라 미세하게 다를 수 있다.

기존 결과를 보존하려면 새 출력 디렉터리로 실행한다. 아래 명령은 백엔드 저장소 PowerShell 기준이며 실행 중인 비교 스택을 사용한다.

```powershell
$comparisonRoot = (Get-Location).Path
docker run --rm --network backtest-compare_default `
  --mount "type=bind,source=$comparisonRoot/comparison/benchmark.py,target=/benchmark.py,readonly" `
  --mount "type=bind,source=$comparisonRoot/.comparison/reports,target=/reports" `
  python:3.15-slim-trixie python -u /benchmark.py --output /reports/scenarios-rerun
```

`benchmark.py --phase normal|boundary|concurrent`로 범위를 좁힐 수 있다. 다른 날짜에 다시 실행하면 외부 시세 수정·캐시 상태·시스템 부하 때문에 결과가 달라질 수 있다.

# 수정된 Rust 버전 재적대 평가 — 2026-11-11

현재 수정본에서 **11개 문제(P1 4개, P2 6개, P3 1개)**를 확인했다. 수정으로 추가된 회귀 또는 새로운 실패 경로는 5개, 수정 전부터 남아 있던 문제는 6개다. 기존 정확성 검사 202개를 모두 통과하지만, 현재 결과를 전반적으로 정확하다고 승인하기는 어렵다.

판정 기준은 독립적인 자금 원장, 달력 일정, 실제 손익과 화면/API 계약이다. Python 결과는 정답으로 사용하지 않았다. 수정 전 Rust 실행 결과는 **회귀 분류에만** 사용했다. 이 감사에서는 애플리케이션을 수정하지 않았다.

## 평가 대상과 증거

- BE/FE: 모두 `rust-migration`. 직전 수정 완료 증거에 기록된 **소스 197개 파일의 SHA-256이 전부 동일**하다.
- 현재 실행 중인 Rust API 이미지: `sha256:08b07b170a82cb9de3ade7b703bd02df4055367917858a89d40bb9fecf375cf0`.
- Rust 콘솔 이미지: `sha256:263444bdab018b109b0dd786880d5e7fa444da2b93f0ae6217142bae7b2cecc2`.
- 일반 Rust 검사: **24 통과**, DB 전용 2개는 일반 실행에서 제외. 별도로 새 캐시 동시성 검사를 임시 MySQL 8.4에서 실행했다.
- 직전 독립 시나리오 **133개 / 검사 202개 전부 통과**.
- 새로운 합성 엔진 시나리오 **16개**, 수정 전 Rust 대조 실행 **16개**, 현재 런타임 이미지 HTTP 요청 **16개**.
- FE는 실제 reducer, 폼 validator, 거래 로그 추출 함수, 주가/비중 차트의 AST에서 추출한 실제 콜백을 실행했다. 동일 함수를 감사 코드에 재구현하지 않았다.
- 캐시: 변경하지 않은 `cached()` / `save()`를 사용해 **500회 스냅샷 교체 + 2,000회 읽기**를 실행했다. 기존 서비스 DB는 사용하지 않았다.

기계 판독용 요약은 `comparison/adversarial/readversarial-evidence-2026-11-11.json`에 있다. 원시 입력과 결과는 `.comparison/reports/readversarial-2026-11-11/`에 보존했다. 아래 금액은 모두 합성 입력의 USD 결과다.

### R01 — 휴장일에 리밸런싱 일정을 소비함

**위치:** `backtest_be_rust/src/engine.rs:282–291`.

시작일 2023-01-01(일), 종료일 2023-02-12, A/B 각각 $5,000, 매주 리밸런싱, 수수료 0. 시세는 평일에만 존재한다. A는 달력일 i에 `100 + 5*i`, B는 100이다.

- 기대: 일요일에 도래한 주문을 다음 공동 거래일로 이월해 1/9, 1/16, 1/23, 1/30, 2/6에 5번 실행. 독립적인 50:50 원장 최종액 **$17,356.30580357143**.
- 실제: **리밸런싱 0회**, 최종액 **$19,285.714285714286**. `none` 설정과 같다. 차이 **$1,929.41**.

달력 일간 평가를 도입하면서 휴장일도 순회하게 됐다. `rebalance_index`를 먼저 증가시킨 뒤 거래 가능한 종목만 고르므로, 일요일 일정은 실행하지 못한 채 사라진다. 수정 전 Rust는 이 반례에서 5번 실행했다. 요청 중 일부 시장만 휴장하는 경우에도 관련 자산의 일정 이월 정책이 필요하다.

**수정 방향:** 평가 달력과 거래 실행 달력을 분리하고, 미실행 리밸런싱을 보류 상태로 유지한다. 월요일이 공휴일인 경우와 서로 다른 시장의 휴장도 검사한다.

**재현:** `sunday_rebalance_weekly_1`, `sunday_rebalance_none`; 동일 이미지 HTTP 200에서 재현.

### R02 — 기술적 전략의 해외 보유 자산이 마지막 주식 거래일 환율로 고정됨

**위치:** `backtest_be_rust/src/engine.rs:575–580`, `630–633`.

RSI(2)로 KRW 자산을 매수한 뒤 보유한다. 2/9까지 현지 종가는 97, 2/10에는 주식 봉이 없고 KRW/USD 환산용 시세만 1,000에서 2,000으로 바뀌는 합성 휴장 상황이다.

- 실제 보유량 **96,938주**, USD 현금 **$597.014**.
- 기대 최종액: `597.014 + 96,938 * 97 / 2,000` = **$5,298.507**.
- 실제 최종액: **$10,000**, 총수익률 0%. 주식 봉이 있는 마지막 날짜의 USD 평가액을 그대로 복사한다.

Buy & Hold 대조군은 같은 휴장/FX 입력에서 $9,700 → $4,850을 올바르게 반영했다. 기술적 전략은 매일의 수량과 현금 대신 이미 환산된 과거 총평가액을 보간하므로 환율 변화를 재평가할 수 없다. 수정 전에도 존재한 문제다.

**수정 방향:** 종목별 현지 수량·가격과 USD 현금 원장을 유지하고, 모든 평가일에 최신 과거 현지 종가와 해당 평가일의 유효 환율로 평가한다. 신호 산출 가격의 통화 정책과 평가 정책을 별도로 정의한다.

**재현:** `fx_open_position_2000`; FX 고정 대조군과 Buy & Hold 대조군 포함, HTTP 200 재현.

### R03 — 캐시 읽기가 하나의 일관된 스냅샷을 보장하지 않음

**위치:** `backtest_be_rust/src/data.rs:204–228`, `239–243`, `131–135`.

같은 종목의 2023년 구간과 2024년 구간을 번갈아 저장했다. 각각 시세 행은 2개다. 메타데이터 SELECT와 시세 SELECT 사이에 다른 요청이 스냅샷 교체를 커밋하면, 이전 구간의 coverage와 새 구간의 시세를 조합한다. 행 개수가 같아서 현재 검사도 통과한다.

**2,000회 읽기 중 캐시 적중 788회, 그중 108회가 행 0개의 History를 유효한 캐시로 반환**했다. 기대는 0회다. 대기나 실패를 강제로 삽입하지 않았으며, 실제 `cached()`와 `save()`는 수정하지 않았다.

이 빈 결과는 `history()`에서 다시 검증하지 않고 메모리 캐시에 저장된다. 이후 계산에서 종목 누락 또는 계산 실패로 이어질 수 있다. 여러 자산 요청은 해당 종목을 경고와 함께 제외할 수 있다. 수정 전의 `history()`에는 빈 결과와 구간 경계에 대한 추가 검사가 있었으며, 새 스냅샷 구현에서 제거됐다. 쓰기 트랜잭션만으로 읽기 두 문장의 일관성은 보장되지 않는다.

**수정 방향:** 메타데이터와 시세를 동일한 읽기 트랜잭션/스냅샷으로 읽거나, 양쪽에 동일한 스냅샷 식별자를 사용하고 교체를 감지해 재시도한다. 구간 검증은 정상적인 휴장일과 동시 교체를 구분해야 한다.

**증거:** `cache-race.json`, `comparison/adversarial/readversarial-cache.rs`. 108이라는 빈도는 이 합성 부하의 관찰치이며 실제 서비스의 발생률 추정치는 아니다.

### R04 — 비중 모드의 종목 추가/삭제가 총 예산을 보존하지 않음

**위치:** `backtest-console/src/features/backtest/model/backtestFormReducer.ts:40–44`, `22`, `138–142`; `components/PortfolioBacktestForm.tsx:56–63`.

총액 $10,000, A 100% 상태에서 종목을 추가하고 B 심볼을 입력한다. 추가 종목은 `weight: undefined`, `amount: 10000`이고 비중 재계산에서 제외된다. A의 $10,000도 그대로 남는다. 폼 검증은 오류 0개이며 실제 요청은 **초기 투자금 $20,000으로 HTTP 200**을 반환한다.

반대로 A 5% / B 95%에서 A를 삭제하면 화면의 총 예산은 $10,000이지만 요청 투자금은 **$9,500**이다. 이것도 검증을 통과한다. 두 경로 모두 수정 전 FE에서 재현되는 잔여 문제다.

**수정 방향:** 비중 모드에서는 모든 항목의 비중 및 정확한 예산 참여 여부를 강제하고, 추가/삭제 시 재계산하거나 명시적인 입력 완료를 요구한다. 제출 직전에 합산 예정 납입금과 전체 예산이 일치하는지 확인한다.

**증거:** `frontend-results.json`의 `addStock`/`removeStock`, HTTP `fe_added_budget`/`fe_removed_budget`.

### R05 — Profit Factor가 실현 손익 대신 수익률의 합으로 계산됨

**위치:** `backtest_be_rust/src/strategy.rs:299`, `329`; `metrics.rs:88`, `101`.

두 번의 청산 거래를 만든 반례에서 손익은 **+$3,540 / −$3,660**, 최종 자산은 $9,880이다. 실현 이익 합계 ÷ 실현 손실 절댓값은 **0.9672131147540983**이다. 이것이 통상적인 Profit Factor 정의다. [TradingView 공식 설명](https://www.tradingview.com/support/solutions/43000681698-profit-factor/)

실제 종목 상세 지표는 **1.3125**, 포트폴리오 요약은 **1.5795217957720904**다. 상세는 서로 다른 원금의 거래 수익률을 더하고, 요약은 일별 평가 수익률을 더한다. 손실인 전략에 1을 넘는 수익성 지표를 붙이는 결과다. 수정 전에도 존재했다.

**수정 방향:** 청산 거래의 수수료 차감 PnL을 기준으로 통일한다. 거래 정보가 없는 Buy & Hold/DCA에 일별 수익률 비율을 같은 이름으로 제시하지 않는다. 일간 지표를 유지하려면 이름과 정의를 구분한다.

**재현:** `profit_factor`, 동일 이미지 HTTP 200.

### R06 — 현금 식별자 변경이 비중 차트와 연동되지 않음

**위치:** `backtest_be_rust/src/engine.rs:192–193`, `435–441`; `backtest-console/src/features/backtest/components/results/WeightHistoryChart.tsx:45–47`, `65–66`.

현금 $5,000 + TEST $5,000이면 현금 비중은 50%다. 수정된 API의 `weight_history`는 `CASH__cash_1: 0.5`, `portfolio_composition`은 `symbol: CASH`를 사용한다. 차트는 composition의 심볼로 조회하므로 **현금 0%, 주식 50%**를 표시한다. 수정 전 결과와 화면 코드의 조합은 **50% / 50%**였다.

F07의 현금/동명 주식 충돌 방지 자체는 필요하지만, 새 식별자를 응답 전체와 FE에 일관되게 전달하지 않았다. 일반적인 현금 포트폴리오에서도 재현된다.

**수정 방향:** asset ID와 표시 심볼을 분리하고 composition/weights/개별 결과/차트 모두 동일한 ID로 조인한다. 단순히 `CASH`로 되돌리면 원래의 동명 주식 충돌이 재발한다.

**증거:** `cash_weight_chart`, `frontend-results.json`의 `cashWeights`.

### R07 — 미청산 포지션의 진입 거래를 화면에서 누락함

**위치:** `backtest_be_rust/src/strategy.rs:223–235`, `333`; `backtest-console/src/features/backtest/utils/chartDataTransform.ts:146–149`; `components/StockPriceChart.tsx:140–169`, `188–205`.

RSI 반례에서 1/5에 96주를 97에 매수했고 종료일까지 보유한다. API에는 `open_positions`가 있지만 `trade_log`는 빈 배열이다. FE가 `trade_log`만 읽으므로 **매수 0회, 매도 0회, 매수 마커 0개**다. 실제 매수는 1회다.

종료일 강제 청산을 없앤 F01 수정은 올바른 방향이다. 하지만 보유 포지션의 이미 체결된 진입을 화면에 전달하는 연결이 빠졌다. 완료 거래 수가 0인 것은 그 정의 아래에서는 맞으므로, 그것을 오류로 세지 않았다. 여기서 문제는 차트의 **매수 횟수와 실제 진입 표시**다.

**수정 방향:** 체결 원장을 청산 거래 통계와 분리하거나, `open_positions`의 진입을 거래 마커에 병합한다. 매도는 만들어내지 않는다.

**증거:** `open_position`, `frontend-results.json`의 `openPosition`.

### R08 — 마지막 항목에 비중 합계 오차 전체를 떠넘김

**위치:** `backtest-console/src/features/backtest/model/backtestFormReducer.ts:23–24`, `334–344`.

허용되는 A 95% / B 10% 입력은 A $9,500, B $500이 된다. 같은 종목과 비중을 B → A 순서로 뒤집으면 B $1,000, A $9,000이다. **같은 포트폴리오의 순서만 바꿨는데 $500의 노출이 달라진다.** 두 입력 모두 폼 검증을 통과한다. 95~105% 허용 범위가 센트 반올림 보정보다 훨씬 크기 때문이다. 수정 전에도 같은 문제가 있다.

**수정 방향:** 합계 100%를 충분히 엄격한 오차로 검증하거나, 허용된 가중치를 전체 합계로 정규화한다. 마지막 항목 보정은 정규화 후의 센트 단위 잔차에만 적용한다.

**증거:** `frontend-results.json`의 `orderPermutation`/`allocations`.

### R09 — 실제 달력과 다른 DCA 최소 기간 검사

**위치:** `backtest_be_rust/src/model.rs:157–161`; `schedule.rs:27–43`.

2023-01-30~2023-03-29, `monthly_2`의 실제 납입일은 **1/30, 3/27**이다. 수정된 FE는 2회라고 계산한다. 하지만 BE는 `2 * 30 = 60일`보다 기간 58일이 짧다며 **422**를 반환한다. 종료일을 3/31로 늘린 60일 대조군은 동일한 2회 납입으로 성공한다.

BE의 30일 근사 규칙은 이전부터 있었다. F03에서 화면과 투자 원장은 달력으로 바뀌었지만 이 검증 경로가 남아 있다.

**수정 방향:** 추가 납입을 요구하는 정책이라면 `schedule(start,end,frequency)`의 실제 결과로 검증한다. 최소 요청 기간 30일 규칙과 DCA 일정 가능 여부를 분리한다.

**재현:** `monthly_2_calendar`, `monthly_2_60day_control`, FE `monthly2Periods`.

### R10 — 계산된 연율화 값의 오버플로가 panic으로 변함

**위치:** `backtest_be_rust/src/strategy.rs:280–289`; `metrics.rs:93`.

입력 금액은 $10,000이고 모든 시세도 유한하고 양수다. 극단적인 상승 시나리오에서 CAGR이 f64 범위를 넘어 JSON `null`이 되면, 상세 통계의 `.as_f64().unwrap()`이 panic한다. 두 합성 사례가 실제 이미지에서 **HTTP 500**을 반환했다.

두 번째 사례는 요청 기간 39일 내 마지막 4일만 시세가 있는 종목으로, 종가 `[100,99,98,1000000]`, 마지막 시가 97이다. 요청 자체는 최소 기간과 금액 검증을 통과한다. API 프로세스 전체가 종료되지는 않았고 이후 정상 요청은 성공했다.

직전 F15는 입력 금액 합산 및 최종 포트폴리오의 일부 필드를 검사하지만, 이 panic은 그 검사에 도달하기 전에 발생한다. 수정 전에도 극단적인 수치 처리 자체는 안전하지 않았으나, 새 `unwrap`이 추가한 500 실패 경로는 회귀다.

**수정 방향:** JSON 직렬화 전에 계산값의 유한성을 검사하고 Result/Option으로 전달한다. 계산 불가 지표의 명시적 처리 또는 422를 반환한다. 종목 상세와 포트폴리오의 기간 정의도 일치시킨다.

**재현:** `finite_annual_overflow`, `finite_short_listing_overflow`.

### R11 — 현금 이름 `date`와 비중 이력의 예약 필드 충돌

**위치:** `backtest_be_rust/src/engine.rs:539–550`, `639–643`; `model.rs:208–218`.

기술적 전략에 `{"symbol":"date","asset_type":"cash","amount":5000}`와 주식 $5,000을 직접 API로 보내면 성공한다. `weight_history[0]`는 `{"TEST":0.5,"date":0.5}`가 되어 **날짜 문자열이 사라진다**. 현금 심볼에는 일반 주식의 대문자 정규화를 적용하지 않고, 충돌 검사도 자산끼리만 한다.

기존 문제이며, 일반 FE는 제출 시 대문자로 변환하므로 이 정확한 입력은 직접 API 호출에 한정된다. 따라서 P3로 분류했다.

**수정 방향:** 자산 데이터를 날짜 등 메타데이터와 별도 객체에 저장하거나, 예약 필드와 충돌할 수 없는 ID로 매핑한다.

**재현:** `cash_date_key`, 동일 이미지 HTTP 200.

## 기존 수정의 재검증 결과와 해석

기존 202개 검사는 모두 통과했다. 다음 시가 체결, 양방향 수수료, 현금 DCA 실제 납입, 지정 총액의 마지막 납입 잔액, 수수료를 반영한 리밸런싱 원장, RSI Wilder 초기값, 달력 일간 위험 지표, 상수 가격의 수치 오차 제거 등 **기존에 검사하던 조건에서는 회귀를 발견하지 않았다**.

새 실패는 대부분 기존 검사가 다루지 않았던 조합이다. 모든 시장이 쉬는 리밸런싱일, 주식 휴장 중 환율 변화, 동시에 다른 구간을 요청하는 캐시, 자산 추가/삭제, API에 새로 추가한 포지션/식별자를 소비하는 화면이 해당한다. 따라서 이전의 202/202 통과를 뒤집는 것이 아니라, 그 검사 범위 밖에서 반례를 추가한 것이다.

이미 TODO에 기록된 정의 불가 지표의 0 대체, 추가 응답 형식/샘플링 정책 등은 새 발견 수에 중복 계상하지 않았다. 휴장일·급등 시세는 합성 입력이며 실제 해당 날짜에 그런 시장 상황이 있었다는 주장이 아니다. 이번 라운드는 새 전체 브라우저 E2E나 실제 외부 시세 공급자의 모든 기업행사 데이터를 검증한 결과가 아니다.

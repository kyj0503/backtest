# T01~T05 수정·독립 정확성 재검증

검증일: 2026-11-11. 백엔드·프론트엔드 브랜치: `rust-migration`.

[4차 적대적 평가](rust-fourth-adversarial-audit-2026-11-11.md)의 **T01~T05를 모두 수정했다.** 재현 입력을 보존해 독립 산식과 오류 거절 기준으로 검증했고, 수정 이미지를 로컬에 반영한 뒤 성능·메모리를 다시 측정했다. Python 금융 출력은 기대값으로 사용하지 않았다.

## 수정 내용과 재현 결과

|---|---|---|
| T01 | 주식 수정종가 누락을 원종가로 대체하지 않고 503으로 거절. 환산용 FX만 누락 시 항등 보정 허용 | 원 OHLC 100·수정종가 50의 40봉은 최종 $10,000/MDD 0%. 첫·중간·마지막 수정종가 누락 및 전체 수정종가 부재는 거절. 가짜 $20,000/−50% MDD를 반환하지 않음 |

| T03 | 볼린저는 첫 완성된 기간의 봉부터 신호 평가, 다음 봉 시가 체결 | 기간 5/20, 수수료 0/1%, 첫 유효 봉/한 봉 늦춘 대조군 총 8개 조합. 수수료 0 최종 $12,375, 1% 최종 $12,139.851485. 기간 미충족 시 무거래 |

| T05 | CSV 수량·단가는 반올림하지 않고 숫자로 왕복 가능한 정밀도로 출력. 금액·수수료는 센트 표시 유지 | 실제 $50 매도 수량 `0.00002500000000000001` 보존. CSV 수량×단가 = $50.00000000000002. 가격 단위를 10^-8~10^8로 바꾼 5개 회귀에서도 $50 유지 |

T02 검증은 Yahoo 파서뿐 아니라 직접 엔진 입력과 DB 캐시 읽기에도 적용한다. 부동소수 보정의 고저가 경계 차이는 8 epsilon 상대 허용 범위로 제한한다. 무효 가격을 작은 양수로 치환하거나 고저가 안으로 강제 보정하지 않는다.

기존 실시장 캡처의 KRW/JPY/EUR 환율에는 일별 종가가 기록된 고저가 범위 밖인 관측이 있다. 환산 경로는 그 **일별 종가를 point rate로 사용**하므로 종가의 양수·유한 값을 검증한다. 그 환율 심볼을 포트폴리오의 거래 자산으로 지정하면 엔진에서 전체 OHLC 검증을 요구한다. 이 구분과 0 환율 거절도 별도 회귀에 포함했다. 기존 일봉 FX의 시간 해상도 가정을 바꾸지는 않았다.

캐시 snapshot 버전을 **3→4**로 올렸다. 이전 스냅샷은 수정주가의 일관성과 OHLC 검증을 보장하지 못하므로 적중으로 인정하지 않고 재조회한다. 기존 DB 볼륨·스키마·사용자 데이터는 초기화하지 않았다. 버전 3 캐시 및 훼손된 버전 4 OHLC의 거절·재조회를 임시 MySQL에서 검증했다.

CSV 금액/수수료의 센트 반올림은 유지하지만, 수량이나 단가 자체가 0으로 사라지지 않도록 했다. 숫자가 매우 작거나 크면 과학적 표기가 나올 수 있으며 CSV 숫자로 다시 읽으면 원장 값을 보존한다.

신규 브라우저에서는 기간 20 볼린저의 $12,375, 상장 전 현금 대기 요청의 연속 성공, 고단가 소수 수량의 **실제 다운로드 파일**을 확인했다. 기존 브라우저에서는 첫 비용, 주간·월간 첫 수익률, 정확한 체결 날짜·가격 툴팁을 재검증했다. 브라우저는 로컬 서비스와 같은 Vite 설정이며 운영 Nginx 프록시는 별도로 검사했다.

첫 검사 과정에서 이전 S04 합성 테스트가 시가만 97,000으로 바꾸고 저가를 110,000으로 남겨둔 것을 확인했다. 해당 테스트의 저가를 97,000으로 수정해 유효한 시가/종가 차이를 표현했다. 금융 기대값·체결 날짜·가격은 바꾸지 않았다. 기존 부분 누락 시세 테스트는 새 거절 계약을 확인하고, 별도의 전 필드 누락 봉은 계속 건너뛰는지 검사한다. CSV 문자열 기대값은 숫자 정밀도 보존 계약에 맞게 갱신했다. Python parity fixture는 변경하지 않았다.

**U01 교차의 동률 처리와 U02 Buy & Hold 비교 시작점은 T01~T05의 범위 밖인 기존 정책 질문으로 유지했다.** 4차 감사의 3,599개 검사 중 나머지 3개는 이 정책 가정과 현재 동작의 불일치이며 새 실패를 숨긴 것이 아니다. 일반 회귀 테스트는 모두 통과했다. 전체 시장·전략 조합의 무오류를 증명하는 결과는 아니다.

주요 회귀 파일:

- `backtest_be_rust/src/yahoo_regression_tests.rs`: 누락 수정종가, 모순 OHLC, 불가능한 체결 거절과 정상 원장 대조군.
- `backtest_be_rust/tests/t01_t05.rs`: 볼린저 첫 신호·체결 인과 관계, 기간 미충족, 엔진 직접 입력과 FX 역할 구분.
- `backtest_be_rust/src/api_tests.rs`, `src/data_regression_tests.rs`: 실제 DB의 상장 전 요청 재현성, 이전/손상된 캐시 재조회.
- 콘솔 `src/features/backtest/services/__tests__/reportGenerator.precision.test.ts`: 단위 변경에 대한 CSV 원장 보존.

## 성능과 메모리 재측정

보존된 `.comparison/reports/corrected-2026-11-11/benchmark-inputs`를 수정 없이 사용했다. **수정 전 Rust도 이번에 다시 실행했다.** 세 구현 모두 CPU 2개·메모리 2GiB, 새 API 프로세스로 시작했다. 32개 시나리오를 각 10회 실행하고 동시 요청 2/8/16개를 추가했다. 각 346건, 총 **1,038건 모두 HTTP 200**, OOM·swap 0이다.

| 구현 | 응답 중앙값 | p95 | 유휴 cgroup 메모리 | 커널 최대 cgroup 메모리 |
|---|---:|---:|---:|---:|
| 수정 전 Rust (S01~S06 완료본) | 4.21 ms | 9.14 ms | 6.63 MiB | 71.26 MiB |
| **T01~T05 수정 Rust** | **4.10 ms** | **9.98 ms** | **3.38 MiB** | **71.11 MiB** |
| Python | 103.32 ms | 274.38 ms | 189.28 MiB | 251.47 MiB |

수정 Rust는 이번 Python보다 중앙값 기준 **25.2배 빠르고**, 최대 cgroup 메모리는 **71.7% 적다**. 수정 전 Rust 대비 중앙값은 2.6% 감소, p95는 9.2% 증가, 최대 메모리는 0.2% 감소했다. 단일 순차 측정의 변동을 포함하므로 작은 차이를 모두 코드 변경의 인과 효과로 해석하지 않는다.

중앙값·p95는 순차 320건의 통합 분포이며 p95는 nearest-rank다. 관측기는 별도 cgroup에서 동작한다. 최대값은 커널 `memory.peak`의 컨테이너 수명 최대이고, 시나리오별 1ms 주기의 관측값은 샘플링 하한이다. cgroup 메모리는 파일 캐시 등을 포함해 RSS와 다르다. RSS high-water는 수정 전 Rust 73.65MiB, 수정 Rust 75.81MiB, Python 251.66MiB다.

이는 **외부 Yahoo/DB 조회와 브라우저를 제외한 고정 시세 API 벤치마크**다. 빌드·브라우저·임시 DB 검사를 종료한 뒤 실행했으며, 라이브 Yahoo 지연 또는 특정 사용자 요청의 성능을 보장하지 않는다. 원시 응답 시간과 시간별 메모리 표본을 보존했다.

## 로컬 서비스와 증거

- Rust 화면: http://localhost:5174/backtest, API: http://localhost:8001.
- Python 화면: http://localhost:5173/backtest, API: http://localhost:8000.
- 네 앱 모두 healthy, restart 0. Python 이미지와 기존 두 DB 볼륨은 유지했다. 검증·벤치마크 전용 컨테이너는 제거했다.
- 실제 로컬 Rust API image: `sha256:43d095916e95fc960b856b422f91ce336cdcb896605fd70a0c8a9374e5771a07`.
- 실제 로컬 Rust 콘솔 image: `sha256:99e4355e40e1b3bdf212351703b57ad6bcf3b7e6c28ad833b234ee1a779fbead`.
- 검증용 최종 이미지와 실제 로컬 실행 파일 SHA256 동일: `9aa7120c71fd3f2317f4db7463ed0075b3a3e62965c1a96fb60f43a74b0d3df2`.
- 검증 소스·fixture·manifest **215개 파일 SHA256**을 고정하고 최종 배포 후 동일함을 확인했다. 커밋·푸시·외부 운영 배포는 수행하지 않았다.

[영구 증거 요약](../../comparison/adversarial/t01-t05-evidence-2026-11-11.json)에 테스트 건수·원장 결과·브라우저 다운로드·시나리오별 성능·실행 이미지·소스 해시를 기록했다. 원시 자료는 `.comparison/reports/t01-t05-2026-11-11`, 수정 전 성능은 `t01-t05-before-memory-2026-11-11`, 수정 후 Rust/Python 성능은 `t01-t05-memory-2026-11-11`에 있다.

재현 도구는 `comparison/adversarial/t01-t05-verify.py`, `t01-t05-browser.cjs`, `t01-t05-smoke.py`, `t01-t05-evidence.py`다. `verify.py prepare`는 이전 감사 입력을 복사한 별도 소스 사본을 만들며, 원래 감사 증거를 덮어쓰지 않는다. 기존 `runner.rs`/`fourth_provider.rs`를 그 사본의 예제로 실행한 뒤 `verify.py evaluate`로 확인한다. HTTP·브라우저 재현에는 DEBUG fixture 모드의 별도 API와 임시 MySQL을 사용한다.

동일 조건의 수정본 성능 재실행:

```powershell

```

수정 전 측정은 같은 Compose의 `memory-rust-api` 이미지에 `backtest-rust:before-t01-t05`만 override하고 동일 관측기·입력·반복 수로 실행했다. 실제 사용한 override도 원시 성능 디렉터리에 보존했다.

> 후속 상태: 아래 S01~S06은 [수정·재검증 보고서](rust-s01-s06-fixes-2026-11-11.md)에서 모두 처리했다. 이 문서는 수정 전 재현 증거를 보존한다.

**잔여 문제 6개(P1 1개, P2 5개)를 재현했다.** 이번에 수정한 11개 문제의 기존 반례는 통과하지만, 계산 결과와 차트·CSV를 함께 정확하다고 판정할 수는 없다.

이번 반례에서는 **11개 수정이 새로 도입한 엔진 계산 회귀를 확정하지 못했다.** 확인한 오류는 기존에 남아 있던 계산/소비 로직이다. 다만 새 미청산 BUY 표시와 복구된 휴장일 리밸런싱이 기존의 잘못된 마커·CSV 로직을 통과하면서, 수정된 기능에서도 오류가 드러난다. 이는 회귀 부재의 증명이 아니다.

Python 금융 출력은 정답으로 사용하지 않았다. 원금·현금·수량 원장, 보정 가격의 단위 변환, 실제 체결 시점, API와 화면/CSV의 수치 대사가 기준이다. 이번 작업은 평가와 재현 증거 추가이며 애플리케이션 소스와 기존 비교 서비스는 변경하지 않았다.

### S01 — 수정주가와 정수 주수의 단위 불일치

**위치:** `backtest_be_rust/src/strategy.rs:237`, `src/data.rs:530–544`.

기술 전략은 USD 환산·보정된 가격에 대해 `floor(자산 × 0.95 / 가격)`로 수량을 정한다. 데이터 모델은 이 보정 단위와 당시 실제 한 주의 관계를 보존하지 않는다. 가격 보정 자체가 문제인 것이 아니라, 보정된 한 단위를 실제 한 주와 동일한 최소 거래 단위로 취급하는 조합이 문제다. yfinance의 공식 문서도 `auto_adjust`를 OHLC 보정으로 정의하고 기업행사 조회를 별도로 제공한다. [yfinance PriceHistory 문서](https://ranaroussi.github.io/yfinance/reference/yfinance.price_history.html)

합성 RSI(2), 원금 $10,000, 수수료 0, 가격 `[1000, 990, 980, 970, 1500, …]`:

- 원래 단위: 980에서 주문 수량 `floor(9500/980)=9`, 다음 시가 970에 매수. 현금 $1,270 + 9주 × $1,500 = **$14,770**.
- 같은 과거 이력이 이후 2:1 분할 기준으로 모두 1/2 가격에 표현된 경우: 엔진은 `floor(9500/490)=19` 보정 단위를 485에 산다. 현금 $785 + 19 × $750 = **$15,035**.
- 당시 실제 1주를 보정 단위로 표현하면 2단위다. 원래 가능한 9주는 18단위여야 하므로 이 원장도 **$14,770**이어야 한다. 엔진의 19단위는 당시 실제 9.5주에 해당한다.

따라서 가격 단위 변경만으로 **$265 / 2.65%p**의 허위 차이가 생긴다. 소수 수량을 사용하는 Buy & Hold 대조군은 양쪽 모두 $15,000으로 불변이다. 수정 전 소스에서도 같은 $14,770 / $15,035를 재현하여 잔여 문제로 분류했다.

**범위:** 이는 동등한 보정 가격 단위에 대한 합성 반례다. 특정 실종목의 Yahoo 기업행사 원본을 재수집해 입증한 결과는 아니다. 당시 원시 체결 가격·주식 분할·거래 단위를 함께 모델링하거나, 보정 단위에서 소수 수량을 허용하는 시뮬레이션으로 명시적으로 정의해야 한다. 정수 실제 주식 거래를 주장하면서 둘을 섞으면 안 된다.

**재현:** `split_unit_1`, `split_unit_0.5`, 소수 수량 대조군 `split_fractional_control_1`, `split_fractional_control_0.5`.

### S02 — 최초 수수료를 비교 성과에서 누락

**위치:** `backtest_be_rust/src/engine.rs:386–394`, `444`; FE `BenchmarkIndexChart.tsx:123–142`.

가격 100 고정, 첫 거래일에 $10,000, 수수료율 1%를 투자한다. 정확한 최종액은 `10000 / 1.01` = **$9,900.990099**이고 납입금 대비 TWR는 **−0.990099%**다. 엔진의 최종액과 요약 TWR는 맞다.

하지만 첫날 `previous == 0` 분기에서 일별 수익률을 0으로 넣고 비용 효과는 내부 `start_ratio`에만 저장한다. 공개 `daily_returns`는 전부 0이다. 화면은 그 일별 수익률만 연결하여 벤치마크 비교 지수를 **100**, 즉 수익률 0%로 만든다. 납입금 100 기준의 정확한 종료 지수는 **99.00990099**다.

이는 최종액 자체의 오계산이 아니라 **요약과 성과 시계열/비교 표시의 불일치**다. 위험 지표에 최초 일회성 비용을 어떻게 포함할지는 정책을 명시할 수 있지만, 비용을 포함한 TWR와 같은 기준을 표시한다면 첫 기준값도 전달하고 적용해야 한다. 최초 수익률에 반영하거나 명시적인 최초 성과 배수를 제공하고 소비자 전체를 맞춰야 한다. 수정 전에도 동일했다.

**재현:** `initial_fee`; HTTP 200, 실제 FE 정규화 콜백의 종료값 100.

### S03 — 주간·월간 차트가 첫 집계 수익률을 버림

**위치:** `backtest-console/src/features/backtest/components/results/BenchmarkIndexChart.tsx:128–137`.

요청 시작 다음 날 가격이 100→120으로 오른 뒤 계속 120인 반례다. 엔진 최종액은 $12,000, TWR는 +20%다. 40일/400일 일간 차트는 지수 120으로 올바르게 끝난다.

800일 요청의 주간 첫 구간(1/8)은 **+20%**를 이미 포함한다. 2,000일 요청의 월간 첫 구간도 **+20%**다. 하지만 차트는 `index === 0`이면 해당 수익률을 읽지 않고 무조건 100을 반환한다. 이후 구간은 모두 0%여서 주간·월간 차트는 **100으로 끝난다**. 기간 길이 때문에 집계 방식이 바뀌면 동일한 실제 +20% 수익이 차트에서 0%가 된다.

S02와 다른 원인이다. 이 사례는 수수료 0이며 BE 일별 수익률도 정확하다. 첫 일간 점이 관례적으로 0이라는 가정을 첫 주·첫 달에도 적용한 오류다. 첫 누적 기준점을 별도로 두거나 집계 전에 정확한 누적 지수를 만든 뒤 샘플링해야 한다. 이 파일은 11개 수정 전 manifest와 해시가 같으므로 잔여 문제다.

**재현:** `front_loaded_gain_40`, `front_loaded_gain_400`, `front_loaded_gain_800`, `front_loaded_gain_monthly`.

### S04 — 체결 날짜와 체결가를 바꾸는 매매 마커

**위치:** `backtest-console/src/features/backtest/components/StockPriceChart.tsx:88–92`, `165–166`.

새 미청산 진입 표시 경로에 800일 RSI 반례를 넣었다. 실제 API 포지션은 **2023-01-11에 95주를 $98에 매수**했다. 주간 가격 샘플은 1/9와 1/16 등을 유지한다. 매핑 함수는 월~일 달력이 아니라 Unix epoch에서 7일씩 나눈 구간을 비교하고, 같은 구간의 1/9를 선택한다. 최종 마커 데이터는 **1/9, 매수 $100**이다.

일간 대조군에서도 실제 매수가 시가 $97, 당일 종가 $110이면 매수 마커의 가격은 **$110**이다. `EntryPrice`를 쓰지 않고 `point.price`를 넣기 때문이다. 엔진 원장의 실제 체결 시점·손익은 이 반례에서 맞다. 잘못된 것은 차트가 보여 주는 날짜·가격이다.

샘플 구간에 거래를 모을 수는 있지만, 실제 체결일과 체결가를 보존하고 집계 표시임을 구분해야 한다. 현재처럼 일반 날짜·매수 가격으로 노출하면 앞선 날짜에 더 높은 가격으로 매수한 것처럼 읽힌다. 해당 차트 파일은 11개 수정 전과 동일하다. **기존 오류가 R07의 새 미청산 표시 경로에도 연결된 것**이며, 이번 수정이 엔진 체결을 앞당긴 것은 아니다.

**재현:** `weekly_backdated_open`, `open_close_gap`. 부가 대조군 `weekly_trade_1`, `weekly_trade_-1`은 여러 거래가 한 마커 점에 합쳐지는 경우를 기록한다.

### S05 — 첫 거래 전 대기 현금과 CSV 자산 열이 사라짐

**위치:** `backtest_be_rust/src/engine.rs:410`; FE `reportGenerator.ts:290–292`.

일요일 1/1부터 요청하고 주식 시세는 월요일 1/2부터 있는 일반적인 경우다. 시작일 $10,000은 아직 매수되지 않은 현금으로 보유되어 `equity_curve`에 정상 반영된다. 그러나 비중 이력은 가격이 없는 주식 계정을 제외하여 첫 행이 **`{"date":"2023-01-01"}`**뿐이다. 현금 또는 해당 계정의 비중을 모두 합쳐 100%여야 하는데 실제 합계는 0%다.

한 종목은 즉시 거래되고 다른 종목은 10일 뒤 시작하는 $5,000 + $5,000 대조군도 대기 현금 $5,000을 누락하여 초기 비중 합계가 **50%**다. 수정 전 엔진에서도 동일하다.

CSV는 자산 열 목록을 전체 구성 또는 전체 이력에서 찾지 않고 **첫 비중 행의 키만** 읽는다. 따라서 일요일 시작 사례에서는 나중에 정상 매수·평가된 주식까지 CSV 전체에서 열이 사라지고, `날짜` 열만 남는다. 화면/CSV에서 대기 현금 계정을 포함하는 완전한 비중 계약과 자산 목록 기준 열 생성이 필요하다.

**재현:** `weekend_cash_weights`, `late_initial_weights`; `weekend_cash_weights.csv`.

### S06 — CSV 리밸런싱 수수료가 거래 수만큼 중복됨

**위치:** `backtest-console/src/features/backtest/services/reportGenerator.ts:281`.

복구된 일요일 리밸런싱 사례에 1% 수수료를 적용했다. 첫 1/9 이벤트의 API 원장은 다음과 같다.

- A 매도 수수료: **$8.33333333**.
- B 매수 수수료: **$8.16831683**.
- 이벤트 총수수료: **$16.50165017**.

CSV의 거래 행별 `수수료($)`에는 두 행 모두 **16.50**이 적힌다. 개별 `trade.commission` 대신 `event.commission_cost`를 쓰기 때문이다. 전체 5개 이벤트의 실제 수수료는 **$66.76780502**인데 CSV 열 합계는 **$133.52**다. 이는 센트 반올림 오차가 아니라 거래 행마다 합계를 반복한 결과다.

엔진의 수수료 원장 자체는 이 사례에서 맞다. 보존된 이전 프론트엔드에도 이벤트 총수수료를 각 거래 행에 쓰는 표현식이 있어 잔여 오류로 판단했다. **R01로 실제 주말 리밸런싱이 복구되면서 그 경로의 CSV에도 노출**된다. 거래별 수수료를 출력하고, 이벤트 합계가 필요하면 별도 합계 행에 기록해야 한다.

**재현:** `rebalance_csv_fees`; `rebalance_csv_fees.csv`.

## 회귀 판단과 한계

기존 202개 검사와 직전 16개 반례의 결과는 유지됐다. 새 반례를 11개 수정 전 엔진에서도 실행했으며, 새 버전의 주요 수치 차이는 이미 의도한 Profit Factor 정의 변경과 휴장일 리밸런싱 복구로 설명된다. 이번 발견을 모두 새 회귀라고 부르지 않았다.

캐시 동시성, 운영 인증·TLS·ARM64, 실제 제공업체 기업행사의 전체 경제적 재구성, 장기 부하/메모리 누수는 재검증하지 않았다. 새로운 성능 벤치마크도 수행하지 않았다. 기존 TODO의 계산 불가 지표 0 대체(A-21) 등을 여섯 발견에 중복 계상하지 않았다. 날짜·가격은 합성 반례이며 실제 그날의 시장을 주장하지 않는다.

저장된 결과를 다시 검증하려면 백엔드 저장소에서 실행한다.

```powershell
python comparison/adversarial/audit.py evaluate .comparison/reports/third-audit-2026-11-11/baseline
python comparison/adversarial/third-evidence.py
```

새 실행은 `third_audit.py prepare` 후 `.comparison/third-audit-crate`를 `/app`, 해당 보고서 폴더를 `/reports`로 마운트한 Rust 도구 이미지에서 `cargo run --offline --example verify -- /reports`로 수행한다. 기존 시나리오는 `/reports/baseline`, 직전 반례는 `/reports/previous`를 지정한다. `third_audit.py before`는 수정 전 소스의 기록된 해시를 확인한 별도 사본을 만든다. 같은 Cargo target을 공유할 경우 실행할 사본의 `.rs` mtime을 직전에 갱신하고 **Compiling 출력**을 확인해야 한다. 이번 수정 전/후 최종 대조 실행은 모두 재컴파일을 확인했다.

HTTP 실행은 사용자 API와 같은 이미지를 별도 컨테이너로 띄워 `DEBUG=true`, `BACKTEST_FIXTURE_FILE=/reports/http-fixtures.json`, localhost 8002를 사용한다. 실제 서비스 DB는 사용하지 않는다. `third_audit.py http`로 실행하고, 감사 종료 후 임시 컨테이너를 제거한다.
